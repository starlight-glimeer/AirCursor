# 产品的三个模块

用户 2026-07-30 收缩后的范围：

| 模块 | 是什么 | 归谁 |
|---|---|---|
| ① **Steam 工坊壁纸** | 用用户的 Steam 账号拉工坊内容并渲染 | 云端 |
| ② **手势** | 手势替代鼠标键盘 | 本地 |
| ③ **音乐交互效果** | 粒子随音乐动（用户指的是 Mineradio 那种） | 云端 |

## ⚠️ ③ 和 ① 是同一个东西（查代码坐实的，不是推断）

用户说"就像 Mineradio 这个音乐播放器的粒子动态交互就是我们想要的"。
而那个粒子交互**就是 ① 已经能跑的那个工坊壁纸**：

| 证据 | 内容 |
|---|---|
| Mineradio 的调用 | `02-visual/00-pointer-cover-particles.js` 里调 `window.MineradioSonicTopography` |
| 它把那东西放在哪 | `public/vendor/sonic-workshop/`（含 `assets/` `project.json` `preview.gif`） |
| 那个 `project.json` | `"name": "Sonic Topography"` |
| 用户给我们的壁纸 | 同一个 `"name": "Sonic Topography"` |

⟹ **Mineradio 不是自研了那个效果，它是把那个工坊壁纸当 vendor 引进来**，
外加一个 `mineradio-bridge.html` 做桥。而**那个桥和我们的 `we-preload.js`
实现的是同一份契约** —— 八个 WE 接口逐个对上，一个不差。

⟹ 所以 ③ 不是要从零做的模块，**是把 ① 已有的能力接上音频**。

### 唯一的差别，而它决定了工作量

| | 音频从哪来 | 要权限吗 |
|---|---|---|
| Mineradio | 它**自己播放**音乐，分析自己的输出 | ❌ 不要 |
| 我们 | ScreenCaptureKit 抓**系统**音频 | ⚠️ 要屏幕录制 + 打包 |

⚠️ 这解释了为什么它那个效果看起来毫无阻碍：**它是播放器，音频本来就在它手里**。
而我们要读用户的网易云，所以绕不开权限。

⟹ 音源已经做成可切换的 provider，所以两条路都留着不冲突。
**"要不要自己放音乐"是产品决定，不是技术问题** —— 待用户拍。

# 两个模块的边界（壁纸/手势的代码分工）

`wallpaper/` 由两个 agent 分工维护。这份文件定的是**谁改哪些文件**和**中间的契约**，
让双方能各自改、各自验，不用读对方的代码。

## 🔴 要测这个分支：用 worktree，别往共享工作区 checkout

**给用户的命令绝不能污染 `~/workspace/AirCursor` 的工作区。** 正确做法：

```bash
git fetch origin
git worktree add /tmp/we-test origin/feat/we-wallpaper
cd /tmp/we-test/wallpaper          # ⚠️ 进 wallpaper/，不是 /tmp/we-test
npm install && npm start
# 测完（一条命令全清掉，不留痕迹）
git -C ~/workspace/AirCursor worktree remove /tmp/we-test --force
```

⚠️ **必须 `cd` 到 `wallpaper/` 子目录。** 这个分支的基点老，根目录 `package.json`
的 `"main"` 还指向 `electron/main.js`（AirCursor 0.4.2 的入口）——
在 `/tmp/we-test` 根目录跑 `npm start` 会启动**错的应用**，而它看起来"能跑"。
（这条是我写完这份文档之后实测发现的，验证过：worktree 里主工作区
`git status` 保持干净、`fetch-vendor.sh` 能正常拉到 24MB vendor。）

### 为什么：我用错误的做法烧掉了用户和另一个 agent 大半天

我曾让用户跑 `git checkout origin/feat/we-wallpaper -- wallpaper/`。那条命令把
25 个文件**写进工作区但不提交**，而 `wallpaper/` 里有一半是手势模块的文件：

| 被覆盖的文件 | 用户看到的症状 |
|---|---|
| `overlay.js`（我的版本在"骨架偏右"修好之前） | **很早修过的 bug 重现** |
| `sensor.js` / `input.js` | 手势变慢、不跟手 |
| `dashboard.html` | 早就删掉的「连续控制」又回来了 |

⟹ **git 里是对的版本，`npm start` 跑的是磁盘上的文件。**
而 `git diff <commit>` 比的是 HEAD、**不含未提交的改动** ——
所以基于 git 的验证会连续四轮说"代码一致"，而问题从一开始就不在它覆盖的范围里。

⚠️ **三个我当时就该知道的事实，我都忘了：**

1. **边界穿过 `wallpaper/` 内部** —— 这句话是我自己写在下面那张表里的。
   "壁纸自包含、只取那个目录"这个念头是错的，那个目录里有对方七个文件。
2. **我给的回滚办法不够。** 我写了「测完 `git checkout main -- wallpaper/`」，
   但那只覆盖已跟踪文件，`we-host.js` 那些新增的会留下。而且我把它写成了
   轻描淡写的附注，没说"不做这步手势会坏"。
3. **用户提示符里一直显示 `main +25 !1`** —— 那 25 个就是我造成的，
   它出现在用户贴给我的每一屏输出里，我看了好几次没注意。
   ⟹ **用户贴的终端输出里，提示符本身是数据。**

### 派生的两条规则

- **任何 checkout / 写文件的命令，必须同时给"怎么完全退出"和"不退出会坏什么"**，
  而且后者要写在显眼处，不是附注。
- **`git fetch` 不能省。** 我还犯过另一个：给 checkout 命令时漏了 fetch，
  于是用户编译的是旧代码，报出和修复前**一模一样的警告和行号** ——
  看起来像"修复没用"，实际是"修复没到"。所以给命令时要附一个
  **能一眼确认拿到新版**的检查（例如 `grep -c <新加的标识>`），
  别让编译/运行结果去背这个责任。

## 🟢 UI 收口（2026-08-01，`ui-2c-0.9.53`）：从"dashboard"到 2C 产品

用户一句话定了方向：**「你的设计太 dashboard 了，我们是一个 2C 的产品」**。
之后 12 轮把面板从"什么都摆在外面"改成"常驻的少、要用时点开"。

### 判据（这一轮反复用到的那一条）

> **常驻的东西要少，而不是功能要少。**

用户为"界面太吵"报了**四次**，每次我都是靠删东西回应，而正确的解法是**收纳**：
右键菜单、弹窗、可折叠的开发者模块 —— 功能一个没少，常驻的从十几个降到 3 行。

### 最终布局

| 位置 | 有什么 |
|---|---|
| 启动页 | 极光背景 + logo，**点一下进去**（没有强制等待） |
| 左栏 | 创意工坊 / 我的壁纸 / 手势录制 + 底部 `⚙ 设置` |
| 我的壁纸 | 轮播摘要行（1 行）+ 壁纸网格。**就这两样** |
| 创意工坊 | 搜索 + 排序 + 三组筛选 + 网格 + 按 ID 装载 |
| ⚙ 设置弹窗 | 壁纸目录行 / 快捷键 / **开发者选项**（折叠，含全部诊断） |

### 用户报出、根因不在"参数"而在"设计"的五件

| 用户原话 | 我原来做的 | 根因 |
|---|---|---|
| 「点了关闭他其实不会关闭，但小圆点消失」 | 关窗≠退出 + 加菜单栏图标 | **我在给一个错的前提补台阶**。前提本身违反 macOS 惯例：把"关闭"实现成了"隐藏" ⟹ 圆点消失但进程还在，两个信号矛盾 |
| 「登录界面只是覆盖了一层什么效果都没有」→「你这个做得太劣质了，还不如没有呢」 | 点 + 近邻连线 | 那是网页背景最烂俗的一种（particles.js 观感）。**问题不在参数，在形式本身** |
| 「开局什么强行等待呀…点击跳过这些都不要」 | 2.2s 进度条 + 自动进入 | **假进度** —— 我们没有任何可测的加载阶段，那条进度条纯粹装出来的，代价是每次启动真的等 |
| 「让壁纸跟着音乐动 这是什么，这应该是默认的」 | 一个 2C 开关 | 它问的是**用户不需要做的决定**：采集条件本来就是"壁纸声明要音频"，默认已经是 system |
| 「只有近期热门一直显示选中的状态」 | — | 真 bug：`className` 在渲染时算，而 onclick 只重画网格。**同一个文件里筛选组有重渲染，排序没有** |

### 两个"我没能实测"的地方（用户侧第一次用就能验）

- **`match_all_tags=false`**（多选取并集）：这台机器没有 Steam API key，
  只能按 `IPublishedFileService/QueryFiles` 的参数表写。
  勾「全年龄」+「13+」出结果 = 生效；零结果 = 参数名不对。
- **极光的观感**：五团、周期 11~19s、亮度 .26~.46 全是我拍的。
  这一版故意**偏强** —— 宁可听到"太晃了"（明确的方向），
  也不要再一次"看不出在动"（那说明白做了）。

### 守卫：这一轮从 199 → 207 项

⚠️⚠️ **搬东西时旧守卫会在正确代码上报红，而那是三条同一个病**：
断言写的是"当时那个位置"，不是它想表达的**意图**。

| 旧断言 | 改成 |
|---|---|
| `#audio-log` 必须在 `tab-mine` 里 | 它的本意是"日志和音源在一起" ⟹ 查 audio-log 紧跟「音源」、中间不许插 `<h3>` |
| 「壁纸层/音源」必须在 `tab-mine` 里 | "在 tab-mine **或**设置弹窗里"，不变的那一半是"不许在创意工坊" |
| Esc 那条用 `[\s\S]{0,300}?` | 锚 handler 的结构边界（**固定长度切片第 9 次**） |

⚠️ 反过来更危险：**搬了三块诊断，一条守卫都没红** —— 那正说明没人守这些。
补的两节重点是"每个诊断 id 只许有一份"（重复的话 `getElementById` 只拿第一个，
而功能页上还留着一份）和"搬完 JS 里要有人绑"（元素在但没人绑，按钮就是死的）。

### 锚点撞名 / 永久绿：这一轮又栽了 6 次

每一条守卫都做了**反向验证**（挨个破坏、确认报红），而其中 6 条第一版是永久绿的：

| 断言锚的 | 撞上了 |
|---|---|
| `cancelAnimationFrame` | `dashboard.js:610` 早就有一个（别的动画用的） |
| `clearRect(0, 0, w, h)` | `dashboard.js:650` 有一模一样的 |
| `.rs-item.now` | `.rs-item.now::before` 那条规则里也有这个子串 |
| `lastMineCount` | 只查名字在不在切片里，而改成 `if (false)` 之后名字还在 |
| `#br-state[^{]*\{[^}]*pre-wrap` | `[^{]*` 跨行匹配到了**我自己刚写的 CSS 注释** |
| `/放不了/` | 我在原处留的解释注释里就有这个词（假阴性方向，第 9 次） |

⟹ 判据收紧成三条：
1. **锚"产生效果的那一句"**，不是变量名/类名/函数名
2. **锚规则的完整形状**（选择器 + 花括号），不是选择器的子串
3. 任何"代码里含不含 X"的断言，**先剥注释和字符串**（`codeOnly`）

### 这一轮的一个流程教训

**版本号 `package.json` 一直停在 0.9.44**，而我在注释和 commit 里一路写到 0.9.53
⟹ 用户每次打包出来的 dmg 都叫 `0.9.44`，面板 build 标识也是。
而那是**用户唯一能确认"我装的是哪一版"的东西** ——
这一轮已经因此浪费过一整轮（我 commit 了没 push，用户报"没看出变化"，
最后靠 commit hash 才分辨）。
⟹ 加了守卫：**代码里出现的最大 `0.9.x` ≤ `package.json` 的版本号**。

## 🟢 鼠标交互链结案（2026-08-02，`0.9.102`）：一个探针推翻了我五个前提

> **转折点是用户那句话：**
> 「你不是应该先搞一堆探针探一探我本地这个权限到底怎么搞的？到底有没有打通，
> 然后再做你的设计呢？」
>
> **他说得对，而这是十几个版本里唯一真正推进的一步。** 在那之前我一直在
> "改代码 → 让他重新打包 → 拿回一个 yes/no"，而这条链有**九个前提**，
> 任何一个断了症状都一样（"点了没反应"）⟹ 我在猜是哪一个，猜错了就再来一版。
>
> ⚠️⚠️ 而探针的价值不只是"测得快"：**它推翻的第一批结论里有我的，也有它自己的。**

### 探针（`scripts/probe-permissions.sh`）测什么

| | 测什么 | 为什么必须是它 |
|---|---|---|
| ① | 装的是哪一版（和仓库版本对比） | 不然全在测旧代码 |
| ② | helper 在不在、可不可执行 | |
| ③ | `codesign` 的签名身份 | 决定 TCC 把它当谁 |
| ④ | TCC 数据库里的辅助功能条目 | 读不到就说读不到 |
| ⑤ | **直接跑 helper**，它自己报 trusted + 数抓到几个事件 | 绕开整个应用的权威口径 |
| ⑥ | 那个壁纸靠什么事件触发 | |
| ⑦ | 配置里那几个开关的实际值 + **写入时间** | |
| ⑧ | **应用自己**那个 helper 在不在跑 | ⑤ 测的是探针启动的，不是它 |
| ⑨ | 页面到底收到了 mousedown / click | 断点在"注入"还是"合成" |

### 它推翻了什么

**① 「监听鼠标需要辅助功能授权」—— 错的，而这个错前提害了六个版本**

```
❌ 辅助功能：未授权（helper 自己报 trusted: false）
✅ 鼠标事件数：148
```

没授权却抓到 148 个事件。而错的来源在 git 记录里写得很清楚：

```
009995a 「证伪：监听鼠标不需要辅助功能授权」   ← 07-30
bd292a4 「初始化 NSApplication —— 零事件的根因」 ← 三天后
```

那次"证伪"实验跑的 Swift 里**零处 `NSApplication.shared`**（`git show` 查过）
⟹ 它的零事件是**那个**造成的。三天后我修了 NSApplication，
**却没回头重跑那个实验** ⟹ 错结论一路传到 0.9.88，成了"把鼠标转发默认关掉"的
理由，还害用户连问六轮"这都需要辅助功能吗"。

> ⚠️⚠️ **教训：一个"证伪"结论的有效期，只到它依赖的前提被改动为止。**

**② 「监听 vs 注入」是两条链，需要的权限不同**

| helper | 干什么 | 要辅助功能吗 |
|---|---|---|
| `GestureWallMouse` | `addGlobalMonitorForEvents` —— **监听**鼠标 | ❌ 不要 |
| `AirCursorPointer` | `CGEvent.post` —— **注入**鼠标事件 | ✅ 要 |

判据：**监听不需要，注入需要**（"控制别的程序"才是辅助功能的语义）。
⚠️ 而 0.9.91~0.9.101 权限面板读的是 `GestureWallMouse` 的 trusted
⟹ 一直显示"未授权"，而那个"未授权"对流星那条链**毫无意义**。

**③ 探针推翻了探针自己 —— 它给出过一个假结论**

```
GestureWall/config.json   Jul 30      dir=null                   ← 探针读的
aircursor/config.json     刚刚        dir=…/粒子效果_网易云监听   ← 真的
```

上一版探针 `for d in GestureWall aircursor; do … break; done` —— **拿目录名的
顺序当优先级**，选中了三天前那个陈旧文件，于是报"壁纸没装载"。
而用户连着两轮说"我就是装载了呀"，他是对的。

⚠️ `app.getPath('userData')` 用 `app.getName()`，它读 package.json 的
**顶层 `name`**（`aircursor`），不是 `build.productName`（`GestureWall`）。

> ⚠️⚠️ **一个给出假结论的探针比没有探针糟** —— 它让我把"装载成功"当成"没装载"，
> 还让用户重复解释他明明做过的事。
> **判据：有多个候选时按 mtime 选，别按我猜的顺序选。**

### 最终答案：链路一直是好的

```
⑨ injected 1713 → 页面收到 mousedown 55 / pointerdown 55 / click 55  ✅
```

**事件链完全通**。流星不出来是**那个壁纸自己的条件**：

```js
pt = We => Ee && K && Pe.current && Pe.current.triggerMeteorAt(x, y)
             ↑ idle 状态
```

`Ee` 由一个 300ms 定时器控制：**音频能量 < 0.05 且持续 3 秒**才为 true
⟹ **只有"安静三秒、壁纸进入待机"之后点击才出流星**，有声音时它自己屏蔽点击。

⚠️ 而用户早就说过「我偶尔触发成功了，但我不确定是不是流星本身会往下坠刚好跟我的手
重叠了」—— 他碰上的正是安静的那几秒，**而他的不确定比我的确定更接近真相**。

### 给下一个人的判据

1. **九个前提的链，别一次改一个然后重新打包** —— 写探针，一次全测
2. **探针本身也要被怀疑**：它的每个路径假设都要回代码核对（我栽了三次：
   userData 目录名、壁纸目录可换、`pgrep -f` 匹配命令行会打到探针自己）
3. **"证伪"结论要标注它依赖的前提**，前提一改就得重跑
4. **区分"不知道"和"没授权"** —— 前者该说不知道，后者才让用户去点

## 🟢 音频圆环结案（2026-08-01）：五个修复，每个都有出处

用户为「螺旋 / 柱子太长 / 半个圆环不动」报了**十几轮**，我猜错约十一次。
**每一次错都是同一个形状**，而最后解决它的是同一条判据。

⚠️ 这一节替换了原来两节已被证伪的结论（「是我诊断工具的残影」、
「那是壁纸故意绕 15 圈的设计」）—— 那两条都被后续实测推翻，
留着会让下一个人照错的方向查。**被推翻的结论要删，不是并列。**

### 用户的第一性原理（这是整轮的转折点）

> 「你为什么是在针对这个壁纸做适配，这很奇怪。应该是我们不理解那个壁纸软件
> 它的渲染原理，所以我们通过这个壁纸去反推我们的渲染器，目的是壁纸到我们的
> 渲染器上效果都不错，懂吗？这才是第一性原理」

⟹ 从"读这个壁纸的代码推该发什么"改成"读 WE 怎么产生"
（出处：`linux-wallpaperengine`，逆向 WE 的开源项目，GPL-3.0 —— **只取算法，不抄代码**）。

### 最终的五个修复

| | 修复 | 出处（不是我调的） |
|---|---|---|
| 1 | **删掉 Hann 窗** | WE 的链子里 `(buf-128)/128` 直接进 `kiss_fftr`，**没有窗** |
| 2 | **128 = 左 64 + 右 64（镜像，两半同一份）** | WE 循环是 `band<64`；数组只有 16/32/64；uniform `64Left`/`64Right` 传**同一个** `audio64` |
| 3 | **stride 2、加权分母 63** | WE 原值 —— 前提 2 改对后，我打的三个补丁全都不需要了 |
| 4 | **`VDSP_SCALE = 0.5`** | 真机自检量出比值 **2.00**（vDSP 的实数 FFT 省了一次除 2，kiss_fftr 没有） |
| 5 | **自检判据改到矩形窗** | 前两条判据（主瓣宽 ≤8、主瓣外要干净）是为 Hann 写的，在正确代码上**恒报 ⚠️** |
| 6 | **采样率 44100、单声道** | `spec.rate = 44100`、`spec.channels = 1`（我们之前是 48000/2 声道 ⟹ 每段频率偏高 8.8%） |

⚠️⚠️ **前五条是 2026-08-01 上午从注释里的算法片段推的；下午拿到了完整源码
（`/tmp/lwe`，即 `linux-wallpaperengine`），它一次定了四个未验前提，并**推翻了我
当天做的两个修复**（分声道、主瓣求和）。⟹ 见下面的第一性原理那一节。

⚠️ 而 **`128 = 左64+右64` 这个布局本身仍是推测**：WE 只有 `audio16/32/64`，
而网页壁纸的 `wallpaperRegisterAudioListener` 收到 **128** 个数 ——
`linux-wallpaperengine` 的 `CWeb.cpp` **压根没接音频** ⟹ 这份逆向源码答不了。
支撑它的是壁纸侧三条间接证据 + 用户实测「镜像后画面明显变好」。

### ⚠️ 三个反直觉的机制（都是算术，不是推断）

**① log10 有一道硬地板，而频段加权是乘法 —— 乘不动 0。**

    power < 1 ⟹ log10 为负 ⟹ 被 max(0,·) 夹成 0
    满幅纯音 magnitude ≈ 425 ⟹ **地板在满幅下方 52dB**

用户实测段 80/100/119 读 0.006/0.009/0.007，反解 magnitude = **1.02**（地板 1.00）
⟹ 那 62 段**不是"值小"，是恒等于 0**。而我为它调了三轮加权 —— 加权改不了地板。

**② WE 能铺满圆环，靠的就是矩形窗的泄漏。**

    旁瓣：矩形 −13dB / 6dB每倍频     Hann −31dB / 18dB每倍频
    magnitude 70 的低音泄漏到 10 段外：矩形 **1.58（在地板之上）**  Hann 0.002

⟹ 泄漏把整条谱抬到地板之上，log10 才有东西可压缩、加权才有东西可乘。
**那不是缺陷，是这套公式的前提。** 而我加的 Hann 窗（教科书上对的事）把它掐掉了。

**③ 动态范围是"离地板多远"的函数。**

    贴地板（magnitude 1.2→2.0，差 1.7 倍）  ⟹ 输出差 **4.4 倍**
    离地板远（magnitude 2.8→12，差 4.3 倍） ⟹ 输出只差 **2.4 倍**

⟹ **「柱子太长」和「柱子太平」是同一个原因**：整体偏大 ⟹ 离地板远 ⟹ 压缩抹平差异。
⟹ 降低整体幅度会**同时**修好两个（地板截断底部 = 放大动态范围）。

⚠️ 我中途推错过一步：说"除以常数在 log 域只是平移、不会压缩"——
**错的**，地板让平移变成压缩（底会先撞 0）。算表核过：K=1→2.4 倍、K=2→5.3 倍。

#### 两个探针，四个前提

我没直接改代码 —— 因为"拿到全 0"是这个项目最熟悉的失败形态
（不报错、画面就是柱子不动、和"没在放歌"长得一样，为它烧过四轮）。

| 前提 | 真机结果 |
|---|---|
| 不需要屏幕录制 | `tapErr 0` + `screenRecordingGranted` **false** |
| 能拿到音频 | 258 次回调、264192 采样、**98% 非零**、RMS 0.2013 |
| 格式 | `bufChannels 2` + `bufBytes 4096` ⟹ **交错立体声**，512 帧/声道 |
| 音量前后 | 音量 26%→53% 而 RMS 只涨 6.7% ⟹ **音量之前**（保留乘系统音量） |

⟹ 这是这一整轮**唯一一次"先量后改"四个前提全齐**的改动。

#### ⚠️ 六个「注册成功但不工作」——这个项目的头号形状

探针 2 一次踩了四个，每个都 `noErr` + 功能死：

| # | 症状 | 根因 |
|---|---|---|
| 1 | `addGlobalMonitorForEvents` 返回非 nil 但零回调 | 没初始化 `NSApplication` |
| 2 | `Timer.scheduledTimer` 注册成功但不触发 | 进程没有主 RunLoop |
| 3 | tap 挂不上（**swiftc 只给警告**） | `&裸CFString` 取地址 ⟹ UID 读成空 |
| 4 | tap 建成功但不监听任何东西 | `stereoMixdownOfProcesses([])` 是**白名单**，空 = 没有进程 |
| 5 | 设备启动成功但零回调 | aggregate device 的 `SubDeviceList` 给空 ⟹ **没有时钟** |
| 6 | 信号处理器不触发 | `DispatchSource` 没被持有 |

⟹ **只查返回码不够。** 必须有"真的读到数据了吗"这一层观测 ——
那就是探针存在的理由，而它这次立刻定位到了每一个。

#### 现在的两条路

    「全系统」        → CoreAudio tap（14.2+）**不要屏幕录制**，无指示
    「只抓网易云」    → ScreenCaptureKit，要屏幕录制，有指示
    macOS < 14.2 / tap 起不来 → 同上，而状态行会说原因

⚠️ tap **抓不了单个 App**：白名单初始化器要 `AudioObjectID`，而从 bundle id
到它是三步链（找 pid → `TranslatePIDToProcessObject` → 建 tap），每步都可能静默失败
⟹ 暂时不做，范围控制在默认路径（也是用户实际在用的那个）。

#### 两个特意防的用户级后果

- **`muteBehavior = .unmuted`** —— 静音 tap 会把音频截走
  ⟹ 症状是"壁纸能动但**没声音**"，而用户会以为播放器坏了
- **SIGTERM 清理** —— 上层用 `child.kill()` 停 helper，而 Swift 默认直接退出
  ⟹ tap + aggregate device 留在系统里，而**每次切音源都会重启这条链**
  ⟹ 残留**累积** ⟹ 可能影响用户的系统音频（症状："某个应用没声音"，
     而谁也想不到是我们留的）
  ⚠️ 用 `DispatchSource.makeSignalSource` 而不是 `signal()` 的 handler ——
  后者只能调 async-signal-safe 的函数，而 CoreAudio 销毁不是
  ⟹ 那种违规可能**死锁在信号上下文里**，比不清理更糟

#### ⟹ 这一节真正的教训

**"我知道"和"我验过"是两件事，而把前者写进 UI 会让它变成别人的依据。**

判据：**若一句话的作用是"关掉一个方向"，它必须有出处。**
（对比：写错一个参数会被下一轮实测打脸；而"这条路不通"没人会去验。）

### 🟢 根因定案：**我们喂的是"系统音量之前"的信号**（2026-08-01，用户实测坐实）

| | 抓取点 | 后果 |
|---|---|---|
| WE | PulseAudio 的 `.monitor` 源 = sink 的**输出流** | **音量之后** ⟹ 音量 50% 则信号 50%，静音时就是静音 |

⟹ WE 的公式是按"音量之后"的信号调的，而我们喂的是音量之前的
⟹ 补上 `samples[i] *= systemVolume()` 是**平台差异的补偿**，不是调参。

#### ⚠️ 这条最值钞的不是修复，是**判据的设计**

我第一版让用户「转音量看面板的 RMS 变不变」，他的回答是：

> 「音乐的高燃节奏时大时 0.2 几、0.3 几，节奏轻柔时 0.0 几、0.1 几。
> 然后是系统音量大的时候**感觉变化不大**？」

**音乐自身的动态（3 倍）比音量的影响还大** ⟹ 那个观测分不出真假，白问一轮。

换成**二元判法**：「系统音量调到 0，柱子还动不动」⟹ 一次就定了（「还真是」）。

⟹ **判据要设计成不受混杂因素影响的形式。**「看某个数变不变」在有动态的
信号上是坏判据 —— 而我当时没意识到那一点，是用户的回答暴露的。

### ⚠️⚠️⚠️ 第一性原理（用户为这条纠正了我**四次**，2026-08-01 定案）

> 「WE 是闭源的，那开发者他必然是不知道我们软件内部的。这些壁纸那么多人创作，
> 他们是怎么创造出来的？他们怎么调出效果这么好呢？**这个版本是他们调出效果 OK 的**，
> 那我们根据这个反推出来一个**不用动的渲染器**才是根本。」

这条的逻辑链，每一步都是事实：

1. WE 闭源 ⟹ 作者看不到渲染器内部
2. 作者只能靠**在真 WE 上看效果**来调参数
3. 那些壁纸发布了、别人用着觉得好 ⟹ **它们在真 WE 上效果 OK 是已验证的事实**
4. ⟹ 若某个壁纸在我们上面效果不对，**一定是我们和真 WE 有差异**

**⟹ 推论（这条最反直觉，我为它栽了三次）：**
**我们观察到的"缺陷"，如果真 WE 上也有，那它就不是缺陷 —— 修它会让画面偏离作者调好的效果。**

| 我"修"过的东西 | 我的理由 | WE 源码说 | 后果 |
|---|---|---|---|
| 加 Hann 窗 | 不加窗会撒假高频（DSP 常识） | `(buf-128)/128` 直接进 `kiss_fftr`，**没有窗** | 泄漏被掐掉 ⟹ 半个圆环恒 0 |
| 分左右声道两次 FFT | 修镜像轴上的等高双柱 | `spec.channels = 1`；`64Left`/`64Right` 传**同一个** `audio64` | 那个双柱真 WE 也有 |
| 主瓣三 bin 求功率和 | 单点采样会抖（实测 0% vs 98%） | `f2 = m_FFTinfo[index].r² + .i²`，**单点** | 抹掉了作者见过的抖动 |

⚠️ 三次的共同点：**观察都是对的，理由都是教科书上正确的信号处理**。
而它们都不是 WE 的行为。⟹ 判据不看"这样做对不对"，只看"WE 是不是这样做的"。

⚠️ 而"针对某个壁纸做适配"有一个**伪装形式**，我也犯过：
2026-08-01 我说过一句**错的**话（下面这句已证伪）：「粒子壁纸为 512 设计，
跑在 WE 上本来就是降级的，所以它的孤峰不用管」—— 它**违反第 3 条**：作者在真 WE 上看着效果满意才发布的。
⟹ "这个壁纸不用管"和"为这个壁纸特调"是**同一个错的两面**。

### 方法上真正起作用的东西

**① 先量后改。** `VDSP_SCALE` 是这一轮**唯一**一个先量后改的常量，
而它一量就精确命中 **2.00**。前面十一个全是先改、再被用户的数据推翻。

⟹ 现在有守卫锁死：这一层的 Float 常量白名单只有三个
（`LOG_SCALE`/`SMOOTH` 是 WE 原值，`VDSP_SCALE` 有真机实测），新增的必须先有出处。

**② 造判据前先问"另一个假设下这个观测会不一样吗"。**
我这一轮差点交付**两个恒真的探针**：

- 同时点亮段 `at` 和 `127-at`，让用户看是否关于 9 点对称
  → 但 PWCircle 的 `deg = i*3` 是线性映射 ⟹ 两段角度中点**恒等于 190.5°**，
    与语义无关、永远对称。**零判别力。**
- 面板报镜像配对的比值
  → 我当时的实现两半发的就是不同频率 ⟹ 比值必然远离 1；
    而"左右声道"假设下我的实现是错的 ⟹ 比值**也**远离 1。两个假设下观测一样。

⟹ 我造探针比检验探针快，而一个恒真的探针会让用户白打一次包。

**③ 报数的口径会随实现一起过期。** 两个方向都栽过：

- **恒绿**：两条「真实数据」测试用的 `REAL_MAGS` 是"用户读数 ÷ 归一化系数"反推的，
  而那个系数改成 WE 算法时就删了 ⟹ 一直在验一组不存在的数字，一直全绿。
  **那就是它们没拦住地板问题的原因。**
- **恒红**：删掉 Hann 窗后，"主瓣宽 ≤8"和"主瓣外要干净"两条判据在正确代码上
  一直报 ⚠️ ⟹ 用户看到 ⚠️ 就以为没修好。

⟹ **删掉一个实现时，要把依赖它的判据一起改。** 而"拿反解的中间量喂公式再验公式"
是循环论证 —— 那条链里没有独立信息。

**④ 守卫要反向验证，而且要枚举等价形式。**
"禁止提前加 0.5"那条我改了四版，**没有一版是靠想改对的**：

    v1 漏了 `magnitudes[index] * 0.5`（最自然的写法）
    v2 太宽，误报 `FFT_SIZE / 2.0`（合法的除 2）
    v3 漏了 `power = magnitude*magnitude / 4.0`（在 power 上除 4 = 在 magnitude 上除 2）
    v4 加上等价形式，三种写法逐个验过

另一条：**子串匹配对"改名"假阴性** —— 反向验证时把 `leakFalloff` 改成
`leakFalloffX`，而 `/leakFalloff/` 仍然匹配 ⟹ 守卫没拦住。标识符断言要带 `\b`。

## ⚠️⚠️ 定位：我们是**渲染器/宿主**，不是"适配某个壁纸"

用户 2026-07-31 点出来的：

> 我们的产品其实是个壁纸渲染器是吧，所以你的修改应该是能够适配这个壁纸的参数，
> 其他的壁纸也可以适配，而不是来一个适配一个

**这条是壁纸模块最重要的判据**，因为我在同一个形状上犯过两次错：

| 我做的 | 错在哪 |
|---|---|
| 把 `USEFUL_BINS = 76` 写成通用常量 | 那个 76 是 **Sonic Topography** 的消费边界（重采样到 512 后 `Pe<=300` 丢掉后半）。而 PWCircle 用 `arr[0..119]`，压根不重采样 ⟹ 76..119 那 44 段在它上面全是 0 |
| 把 clamp 上限写成 `min(1.2, …)` | 1.2 是 **PWCircle** 的内部上限（`Math.min(w1, 1.2)`），不是 WE 的契约 |

⚠️ 两次都是**拿单个壁纸的实现细节当契约**，而且第二次是在我刚为第一次写完检讨之后。

### ⟹ 判据

**如果一个数只能从"某个壁纸的源码"推出来，它就不该在这一层。**

能留在音频层的，必须能从这两者之一推出来：
- **WE 原版的行为**（可以从壁纸代码**反推**，但推出来的是"WE 长什么样"而不是"这个壁纸要什么"）
- **信号处理本身**（每个箱子要有独立的 bin、防 NaN、压 FFT 逐帧抖动）

⚠️ **这一节原来举的例子本身就是这个错的第三次。** 它写着：

> 例：`NORMALIZE = 0.06` 的依据是"PWCircle 的 `w1*range*100` 且 range 默认 9
> ⟹ 一根 90px 的柱子对应 w1≈0.1"

**三处都错**：① `range` 是 `properties.range.value / 5` = **1.8**，不是 9
⟹ 我把柱子长度算大了 5 倍；② "90px 的柱子"是我目测的，没有出处；
③ 那个 0.06 是从**一个壁纸**的像素反推的，正是这一节要禁止的做法。
⟹ `NORMALIZE` 已经删了（现在这一层没有归一化系数，见音频圆环那一节）。

### 哪些是契约、哪些不是

| 在音频层 | 归属 |
|---|---|
| 128 段 = **左 64 + 右 64（镜像）** | ✅ 契约（WE 循环是 `band<64`、uniform 是 `64Left`/`64Right`） |
| `0.35*log10(power)` + 频段加权 `2−e^((1−band/63)−0.5)` | ✅ 契约（WE 原式，逐字对上） |
| **做时间平滑，两向同系数 0.3** | ✅ 契约 —— WE 原版就是 `movetowards(cur, target, 0.3f)` |
| **不加窗函数** | ✅ 契约 —— WE 的 `(buf-128)/128` 直接进 `kiss_fftr`；泄漏是它铺满圆环的机制 |
| `VDSP_SCALE = 0.5` | ✅ 但只因为**真机量出比值 2.00**（vDSP vs kiss_fftr 的库约定差） |
| 具体截到 1.2 / 具体衰减 0.75 / `USEFUL_BINS=76` | ❌ 壁纸的事，不该出现在这一层 |

⚠️ 上面第三行**曾经写的是"不做时间平滑"**，理由是"壁纸自己会平滑、我们再做是双重平滑"。
**那和 WE 的真实行为相反** —— 而壁纸作者是对着 WE 的行为调效果的，
所以"双重平滑"恰恰是对的。⟹ 又一次：我的推理 vs WE 的实际行为，听后者。

`test/audio-bins.test.js` 里两条守卫查这个：
① 已知只属于某个壁纸的数字（`1.2` / `0.75` / `300`）不许出现在代码里；
② 这一层的 Float 常量**白名单只有三个**（`LOG_SCALE`/`SMOOTH`/`VDSP_SCALE`），
新增的必须先有出处。

## 契约：手势事件

手势模块产出，壁纸模块消费。**这条线定死之后，双方各自可验**：

```jsonc
// 连续量：每帧发，0..1 的绝对值（不是增量）
{ "v":1, "kind":"gesture", "action":"zoom",     "value":0.62, "at":1785… }
{ "v":1, "kind":"gesture", "action":"pointer",  "x":0.4, "y":0.7, "at":… }

// 离散：触发一次
{ "v":1, "kind":"gesture", "action":"swipeLeft", "at":… }
{ "v":1, "kind":"gesture", "action":"spin",      "at":… }   // 用户录的手势
```

**为什么 `zoom` 发绝对值而不是"放大多少"**：渲染侧决定映射到什么倍数（`config.zoom`
的上下限），判定侧只报"手在干什么"。这样两边的调参互不干扰 —— 手势模块调灵敏度不会
改变壁纸的缩放范围。

**动作 id 是共享词表**，定义在 `templates.js` 的 `ACTIONS`。加动作要两边都知道：
手势模块负责它能被录制/触发，壁纸模块负责它触发之后有反应。⚠️ **改 id 等于让用户
已录的手势静默失效**，只能加不能改。

## 契约：骨架关键点

```jsonc
{ "hands": [[{ "x":0.4, "y":0.6 }, …21 点]], "recording": true, "at":… }
```

归一化、**已镜像**（发出前就翻好，接收方不用再想这件事）、不含 z。
`sensor.js` 发 → `main.js` 转 → `overlay-window.js` 画。

## 已知问题：手势不灵敏（手势模块）

用户反馈"骨架很大，而且不灵敏"。骨架大是渲染问题，已修（见下）。**不灵敏没查**，
可能的方向按可疑度：

1. **`modelComplexity: 0`**（`sensor.js`）。为省算力选的，代价是关键点精度。AirCursor
   用的是同样的值，但它的用途是指针定位，对精度更宽容。
2. **`SEND_INTERVAL_MS = 33`**（~30/s）。渲染侧有 One Euro 平滑，理论上够；但如果实际
   摄像头帧率就只有 30fps，节流会把有效采样率砍到更低。
3. **`gestureTuning` 的默认值**。`minCutoff: 1.2` / `beta: 0.045` 直接抄的 AirCursor，
   而那是给**屏幕指针**标的 —— 壁纸的视角控制是完全不同的量级，抄过来没有重新标定。
4. **`deadzone: 0.0016`** 归一化后相当于屏幕的 0.16%。看着很小，但 `input.js` 把坐标
   乘到 `FILTER_SPACE=1000` 的虚拟像素空间里滤波，所以实际死区是 1.6px —— 那个数是
   AirCursor 为**像素级指针**标的，对"手挥过半个屏幕"这种量级可能过小或过大，没验。

⚠️ 第 3、4 条是同一类问题：**AirCursor 的调参是为它自己的用途标定的，搬过来没有重标**。
`pitfalls.md` 里"一份报告只能标一个常数"说的就是这件事。

## 刚修的：骨架太大

`toCanvas` 原来把归一化坐标直接乘满屏 —— 手在摄像头里占 25%，在 1470px 宽的屏上就
画成 368px，比真手大好几倍。

现在**位置铺满屏、尺寸压到固定手宽**（200px 或屏宽 14%，取小）。两者分开是关键：
位置要覆盖整个屏幕才指得到任何地方，尺寸不能跟着屏幕长。只缩不放 —— 手离得远时
强行拉大会把"手离得远"这个信息抹掉。

## 跨文件不变量（两边共有，最容易分叉）

这些是**两个文件之间**的约定，任何一侧的单测都看不见。分叉的后果都是静默的：

| 不变量 | 在哪 | 分叉的症状 |
|---|---|---|
| 开骨架窗口的条件 == 发关键点的条件（录制时都放行） | `main.js:syncOverlayVisibility` / `sensor.js:sendHands` | 关骨架后录制 = 空窗口，和"骨架坏了"分不清 |
| 归一化坐标在喂给 AirCursor 模块前乘到 `FILTER_SPACE` | `input.js` | 掌宽被 `Math.max(60,…)` 钳死 ⟹ 速度恒为 0 ⟹ 挥动永不触发 |
| 加载 `templates.js` 的窗口必须先加载 `system.js` | 各 `*.html` | 八个系统动作静默消失，UI 上那一栏是空的 |
| 动作 id 只加不改 | `templates.js:ACTIONS` | 用户已录的手势静默失效 |

`test/gating.test.js` 和 `test/system.test.js` 里各有守卫读源码盯着前三条。

## 协作规则

### ⚠️ 2026-07-31 起：壁纸侧由云端 agent 全权负责

用户原话：「**看来这样来回修复不行，容易出问题，你就全权负责了，出现解不了的问题，
我再问他**」。

背景：那天我们两个 agent 在**测试工具**上来回改了五轮（`ea22921` → `23da003` →
`6c0a297` → `a7f7306` → `50a5c94`），而用户最初报的**壁纸问题一直没查**。
每一轮修的都是真东西，但往返本身有成本，而且制造了新的出错机会 ——
其中一次我用 `git stash` 判基线，差点第三次删掉手势侧的 `quitting` 修复。

⟹ **现在的规则**：

| | |
|---|---|
| 壁纸侧（含合 main） | 云端 agent 自己收尾，不逐轮往返 |
| 手势侧 | 本地 agent |
| 解不了的问题 | 用户会去问另一边 —— 尤其权限/打包/手势判定 |
| 两份日志 | 继续写。**读是为了不重复劳动，不是为了回应。** |

⚠️ 这不改变边界的用途：**避免同时改同一处**仍然重要。动共享文件
（`main.js` `dashboard.js` `dashboard.html` `preload.js` `package.json` `test/`）
前先看对方日志的最新一条。

⚠️ 也不改变破坏性操作的门槛：**删远端分支 / 部署 / 对外发东西仍然要用户点名。**
"全权负责"是关于技术决策，不是关于不可逆的外部动作。


**「我改了什么」写进 `aicursor-helper/CHANGELOG-CLOUD.md`**（云端 agent 维护，
倒序、只增不改、一条几行）。每条标注三件事：碰了哪些**共享文件**、有没有碰对方的
**模块文件**、**要不要对方做事**。

⟹ 为什么单独一个文件：`TO-LOCAL.md` 已经 30KB，追加式文档的问题是
**要知道"新增了什么"得读一整本**。而两个 agent 协作里"对方做了什么"必须一眼扫完。
详细设计仍然留在专题文档里，那两者是不同用途。

**读法**：从上往下读到自己上次看过的那条就停。

⚠️ **两份，对称。** 本地 agent 的那半在 `aicursor-helper/CHANGELOG-LOCAL.md`。
用户的要求是「**我不希望你们有信息差**」—— 单向日志只解决一半：对方做了什么你知道了，
你做了什么对方仍然不知道。（实例：本地删了四个远端分支，云端完全不知情。）

⚠️ **过期条目要清掉，不是留着。** 那份 `TO-LOCAL-RESUME.md` 里曾有三条"缺口"
在对方已经补完之后还留着 —— 而**过期文档比没有文档更糟**：它会让人去做已经做完的事，
或者按一个不成立的前提推理。


**commit message 写清楚三件事**：改了什么、为什么（尤其是"为什么不用更显然的那个做法"）、
**什么没验证**。最后一条不是客套 —— 云端跑不了 Electron/摄像头，UI 和真机行为一律未验，
说清楚才不会让对方以为验过了。

**改到对方文件时**：先在 commit message 里说明为什么必须动，或者更好 —— 在契约里加一个
字段让对方自己改。

⚠️ **分工是效率选择，不是权限边界。** 用户对我们两个都说过：「你权力很大，什么都能做，
只是我让你专注于X了，另一个专注于Y，更加高效。就是要注意你做了什么，另一个要知情。」

⟹ 碰到对方模块里的**真 bug 直接改**，不要停下来问"这归谁"（那会把本可做完的事变成
一轮往返，而用户还得当传话筒 —— 正好抵消了分工换来的效率）。义务只有一条：**写清楚**。
措辞上也别写成"顺手修你两处"，那是在解释自己越界。

⚠️ **但这条不覆盖破坏性的外部操作。** 删远端分支 / 部署 / 对外发东西 —— 先问用户，
**哪怕判断已经成立**。实例：本地 agent 自己写了"那是不可逆的 —— 要删吗"，然后没等回答
就删了四个远端分支（打了归档 tag，所以可逆，但流程是错的）。

⚠️ **守卫尽量写成独立的 `check(...)` 块，别塞进对方也会改的 check 里。**
实例：本地 agent 在一次合并里取对方的 `gating.test.js` 为底，**塞在共享 check 里的
两条断言跟着丢了**，而丢守卫不会红 —— 当时报的是"121 条全绿"。

⚠️ **`node --check` 只验语法，不验"我想加的东西加上了"。** 同一次合并里补回自己改动的
脚本第三步失败，而只看了"语法 ✅"就往下走 ⟹ 两条日志通道静默消失。
**有副作用的批量改动之后要查状态，别只看不报错。**

**跑测试**：`npm test` 是全量，改哪块至少跑对应的那几个文件。`npm run check` 只查语法，
**查不出未定义的标识符** —— 我在这上面栽过（`spawnSync` 没导入，运行时才炸，症状是
"手势触发了但什么都没发生"）。`test/system.test.js` 现在有一条守卫读 `main.js` 源码
检查导入完整性。

## 测试能覆盖什么、不能覆盖什么

205 项纯逻辑用例，`node` 直跑，不需要 Electron / GPU / 摄像头。它们覆盖几何、数值、
状态机、单位换算、接线完整性。

**覆盖不了**：画出来好不好看、真手能不能被认出来、窗口层级在真机上对不对、灵敏度合不合适。
夹具是合成的（规则形状的假手、纯色像素），真手的抖动、丢帧、时间相关噪声全在外面。
所以任何"手感"类的判断都只能真机看。

## ③ `mergeConfig` 里 `base === null` 那一行不能删

`typeof null === 'object'` ⟹ `typeof base !== 'object'` 那道闸**拦不住 null**
⟹ `Object.keys(null)` 抛 TypeError ⟹ `readConfig` 回默认值
⟹ **用户所有设置静默丢失**。

⚠️ 而"默认值是 null"在这个 config 里是**常态**（语义 = "还没设过"）：
`we.dir` / `we.steam.*` / `we.ai.apiKey` / `we.steamCmdPath` / `layers.*`
⟹ 任何存过这些值的用户**每次启动都会踩**。

⚠️⚠️ 这个 bug 藏了几个月，因为 `readConfig` 用的是**裸 `catch {}`**。
⟹ 判据：**`catch {}` 不写理由，就是在赌"这里只会因为我想到的那个原因失败"。**
那个 catch 想兜"文件不存在 / JSON 坏了"，而它顺手把"我们自己的代码抛异常"
也兜了 —— 后者的正确反应是**吵**。

⟹ 壁纸装载在 `releaseWallpaperGate()`，挂在**已有的** `launch-dismissed` 信号上

⚠️ 判据：**已经有一道闸门就挂上去，别开第二道** —— 两道闸门各自超时各自兜底，

⚠️ 兜底 **8 秒**，比骨架的 20 秒**短** —— 那个差是有理由的：面板 JS 挂了信号

## ⑤ AI 生成壁纸：闸门是**代码**，不是模型

实测（Bedrock Sonnet 4.5，真跑）：一轮生成能过大半硬约束，剩下的靠
「机器闸门 → 回喂 → 再检」三轮收敛（v1 262 行 1 问题 → v3 343 行 0 问题）。

⚠️⚠️ 而同一次实测里让模型审自己的产物，它**判错两次、方向还相反**：
- 鼠标**完全没接**（全文只有一个 `addEventListener`，是 resize）→ 它判 **pass**（漏报）
- `Math.random` 只在粒子诞生时用（是对的）→ 它判 **fail**（误报）

而 `grep e.buttons` / `node --check` / `grep -c addEventListener` 三条随手一跑
就把漏报逮住了，零成本零假阳性。

⟹ **判据：能用代码判的必须用代码判。** 三层闸门：
① `Gen.inspect`（纯函数，有测试）→ ② 隐藏窗口跑 3 秒 → ③ **用户的眼睛**
（"好不好看"只有他能判，所以这一层不放任何模型判断）。

⚠️ 而**误报比漏报贵**：误报会让模型去改一段本来正确的代码，而它照改之后
可能真的改坏。所以 `gen.test.js` 里专门有一组**误报守卫**（8 条，标着"不误报"）：
data URL 不算外部依赖、注释里的网址不算依赖、`1000/30` 那种限帧写法也认、
`&&` 形式的接口保护也认、离屏窗口 15fps 不算"几乎不动"、99.25% 近黑不算全黑。

⚠️⚠️⚠️ **探针支持两种协议，而只有一条分支被走过**（0.9.144 真事故）：
`ping()` 只认 OpenAI 的 `data.choices[0].message.content`，而 Bedrock 的正文在
`data.content[0].text` ⟹ 用户实测"通了"但 `回了「」`。
⚠️ 那**比报错更坏** —— 它让人以为模型有问题，而其实是我这边读错了字段。
⟹ 判据：**一个函数支持两种协议时，两条分支都要有人走过。**
`chat()` 那边一直是分开处理的，探针漏了 —— 因为它是后加的，
而当时默认提供方是 DeepSeek（另一条分支）。
⚠️ 两家的差异不止正文位置：`stop_reason` vs `finish_reason`、
`output_tokens` vs `completion_tokens`、thinking 块 vs `reasoning_content`。

## ⑤f 先复刻一张，再泛化 + "审美"里能机器判的那部分

用户 2026-08-03：「先生成一个具体的，就是目标能生成我这张，就通过提示词来复刻出
我这张壁纸的效果，然后实现以后我们再把它泛化，那我理解这种类型我们就拿下了」

⚠️⚠️ 随机挑 12,096 种组合的问题**不是"不够多样"，是每次目标都不一样
⟹ 一次都收不敛**（用户连着看到三张都"抽象不好看"）。
⟹ 判据：**先把一个目标做到位，再放开维度。** 前三张走 `REFERENCE`（固定配方
+ 实测规格），第四张起自动换随机配方。

⚠️ 而这**同时把验收标准从"好不好看"变成"像不像"** —— 后者能量化。
参考壁纸 `preview.gif` 200 帧逐帧量化的结果：

| 指标 | 参考壁纸 |
|---|---|
| 近黑(<25) | 17-45%（随音乐呼吸） |
| 高亮(>120) | 4-21% |
| 上 1/3 亮度 | 恒定 ~25（背景，主体不占它） |
| 中 1/3 | 58 → 110（主体在这） |
| 下 1/3 | 15 → 71（波纹扩散到前景） |
| 底色 | `#070815` |
| 主色相 | 洋红紫 290-330（40%）→ 激烈时蓝紫 210-260（60%） |
| **饱和度中位** | **0.30-0.34**（激烈时才 0.65） |

⚠️⚠️ 饱和度那条最容易丢，而它是"一眼就俗"的主因 —— **低饱和才是"高级感"**，
而模型默认给高饱和霓虹色。

⛔ **两层软判定，而它们测不到的东西要说清**：
- `judgeComposition(probe)` 从像素判：铺满 / 全亮 / 上方太亮 / 主体不在中间 /
  颜色太艳 / 没有明暗层次
- `inspectDesign(code)` 从代码判：元素太少 / 视角太高 / 只有一种动态
  ⟹ 判据：**能从代码读的就别猜像素**（俯视和低视角在三带亮度上可以完全一样）

⚠️⚠️⚠️ 我拿用户那次"很抽象不好看"的**真实探针数据**跑了 `judgeComposition`：
近黑 74%、三带 20/70/40、饱和 0.55 ⟹ **零问题**。
那不是判定器坏了 —— 那张的问题（256 根柱子、只有整体膨胀、俯视 (0,14,18)）
**在像素分布上测不出来**。所以才有了 `inspectDesign`。
⟹ 判据：**说清一层闸门测不到什么，比夸大它测得到什么重要。**

⚠️ 两层都是**软的**：进 problems 触发下一轮修，但三轮之后**仍然落盘交付**
（`softOnly: true`）—— 构图是审美，判错了不该让用户拿不到壁纸。
⟹ 硬闸门拦"必然出事"（黑屏/报错/不动），软判定只给数字。

⛔ **两个校准基准，测试里守着**：
1. 参考壁纸的实测值 ⟹ 必须零问题（目标本身通不过就是阈值错了）
2. `scene.example.js` ⟹ 必须零问题（那是用户真机验过"能看"的）
⚠️ 我第一版视角阈值 0.55 就把 ② 判红了（它是 (0,15,26)，y/z=0.58）⟹ 放到 0.75。
判据：**一条闸门把已知可接受的产物判红，就是阈值错了。**

## ⑤b 骨架：锁"会坏的"，放"影响观感的"

⚠️⚠️ 0.9.139 之前是**让模型从空写整个 `index.html`** —— 而那做不到"稳定"：
三轮收敛出的是 300 行 canvas 2D，而用户给的参考壁纸是作者 v1→v15 迭代出来的。
⟹ 拆成两半（`wallpaper/skeleton/`）：

| | 谁写 | 里面是什么 | 为什么在这半边 |
|---|---|---|---|
| `runtime.js` + `index.html` | **人**（验过、有 13 条测试） | WebGL 上下文 / 相机 / 40fps 限帧 / dpr 上限 2 / resize / 音频解析 / 宿主接线 / 错误上报 / 3 秒自检 | 坏了壁纸就废，而它们**没有"风格"可言** |
| `scene.js` | 模型 | 元素怎么摆、音频映射到什么、配色、运动、**底色/雾/灯光/相机** | 那是设计，锁死它等于每张都一样 |

契约只有三个函数：`SCENE.build(ctx)` / `frame(ctx)` / 可选 `layout` `reconfig`。

⚠️⚠️⚠️ 而 0.9.138 我把**底色 / 雾 / 灯光**也锁在骨架里了 —— 那三样正是
"第一眼"看到的东西 ⟹ 每张壁纸都是"深蓝黑底 + 同一种打光"，必然像。
0.9.140 改成"默认值"：`scene.fog` / `scene.background` 是起点，默认灯光装在
一个 Group 里（`ctx.defaultLights`），模型一句 `scene.remove(ctx.defaultLights)`
就能换整套。
⟹ **判据：锁的边界是"坏"和"丑"，不是"我能想到的"。**

⚠️ 骨架里每条 `⚠️` 都是实测栽过的坑，其中三条最容易被"顺手优化"掉：
- **音频必须 `Math.max` 累积峰值** —— 直接赋值会让两帧之间的峰值被后一帧的
  低值抹掉，症状是"不跟音乐"（而日志完全干净）
- **`frameErrors > 30` 之后停掉 rAF** —— 每帧都抛的话每帧都报会灌满日志、
  堵死 IPC
- **`window.__dpScene` / `__dpDiag` 不进 `we-preload`** —— 那是我们自己骨架的
  内部观测点（探针靠它判"就绪"），不是给第三方壁纸的契约

## ⑤b2 "画面一片黑"的三个根因（0.9.147 实测）

用户 2026-08-03 实测："这次的效果看起来一片黑"，读数是
**场景 1 个对象、高亮 0%、三带 12/9/6**，而三轮修下来一动没动。

⚠️⚠️ "1 个对象"是关键：骨架默认往场景里放了一个 `defaultLights` Group
⟹ 只有 1 个意味着**模型删掉了默认灯光**（或者一个都没加）。

| 根因 | 症状 | 为什么难查 |
|---|---|---|
| 删了 `defaultLights` 还用 `MeshStandard/Phong/Lambert` | **纯黑**（字面 0,0,0） | 那不是"暗"，调亮度系数**完全无效** |
| 建了 Mesh 没 `scene.add(...)` | 什么都不显示 | **不报错** |
| 元素在相机背后 / 视锥外 | 什么都不显示 | 不报错，而坐标看起来"很合理" |

⟹ 新增闸门 `C2-删了灯还用需光材质` / `C3-没加进场景`。
⚠️ `C2` **不是"不许删灯"** —— 0.9.140 特意放开了灯光（见 ⑤b）。它拦的是
"删了灯 + 需光材质 + 不加灯"这个组合，而报错里给**两条出路**
（换 `MeshBasicMaterial` / 自己加灯）。

⛔ **而更深的问题是回喂**：三轮都没修掉，因为回喂里只有"太暗了"这种**现象描述**
⟹ 模型改的是颜色的 L 值，而那改不动"没有光"这个根因。
⟹ 判据：**回喂要给根因，不是给现象。**
现在同一个问题 id 连着两轮出现时，提示词里会明说"上一轮那样改没用，
别再微调同一个地方"，并给出 4 个候选根因。

⚠️⚠️ 另外 `judgeComposition` **只判了区间的一头**：判了"太亮 >45%"和
"铺满 <8%"，却漏了"太暗"—— 而用户那次高亮是 **0%**，六条判定只报了一条。
⟹ 判据：**一个区间要判两头。**
⚠️ 而 `R-画面全黑`（近黑 >99.5%）也没报 —— 它有 50% 近黑，不是"全黑"，
是**"有东西但全都很暗"**。那是两种不同的失败。

⚠️ 提示词里之前**一个字都没提这个陷阱**（`MeshBasicMaterial` / `defaultLights` /
`纯黑` 三个词全缺）。现在写代码那步有一张"材质 vs 需不需要灯"的表 +
三条合法组合，设计那步要求说清材质和灯的搭配。

## ⑤h ReAct：先给现场，再给结论 + 能算的别让模型猜

用户 2026-08-03：「不一定就是纯靠 prompt 去驱动 agent，你也可以适当增加一些脚本」
「agent 的 skills / tools 这些东西肯定都是要正常的配给他的」「思考方式 react 可能比较好」

### ① 能用公式算准的，别让模型猜（`palette.js`）

⚠️⚠️ 实测那次：模型自己推亮度公式，写成
`lum = 0.4*(1-dd)*(1-dd)` 然后又 `lum *= (0.1+0.9*(1-dd))`
⟹ 三次衰减、外圈纯黑、画面高亮占比 **0.0%**。
而它自己的注释里写着"根因分析：上一版把 lum 一路乘小" ——
**诊断对了，改的时候又犯了一次**。

⟹ `palette.js` 把亮度/饱和度/色相算成**三个纯函数**（数字全来自参考壁纸实测），
并生成一段 `DP` 代码**注入进模型的产物**。
⚠️ 模型该决定的是"什么形状、什么运动"（那是设计）；
"距离 0.7 处的亮度该是多少"是**算术**，算术交给代码。
⛔ 注入的字符串和测试用的函数**必须算出同样的值**（测试里守着）——
否则我测的和模型跑的是两回事。
⚠️ 边界检查在**入口**做一次（`clamp01`），别在下游重复兜 ——
`hueAt` 走 `% 360`，没有下游兜底，NaN 会直接漏出去。

### ② 回喂给现场，不给结论（`buildObservation`）

⛔ 原来是"模型盲写 → 我们判 → **回喂一句结论**"，那不是 ReAct，是改作业。
⟹ 现在回喂时**先给观测数据**（真跑的帧数 / 32×32 像素分布 + 目标区间 /
**从它自己代码里量出来的事实**），检查器结论排在后面。

| 给判断（旧） | 给事实（新） |
|---|---|
| `[C-太暗了] 把亮度提上去` | `高亮 0.0% ← 目标 5-20%` |
| | `亮度变量被 *= 了 1 次：lum *= (0.1 + 0.9*(1-dd))` |
| | `场景里有 1 个顶层对象（骨架默认放了一个 defaultLights Group ⟹ 只有 1 个说明你删了它或什么都没 add）` |
| | `材质：MeshBasicMaterial；删掉了 defaultLights；没有自己加灯` |

⟹ 判据：**给"你写了什么"的事实，比给"你错了"的判断有用。**
我的判断会把它往一个方向推；原始数据让它自己连因果。
⛔ 观测报告里**不许出现判断词**（"太暗了"/"像个圆锥"），测试守着。

### ③ 要求它先写诊断（`===SCENE===` 分隔）

回喂的输出格式是两段：诊断（把数据和代码连起来）→ `===SCENE===` → 完整代码。
⚠️ 那一步**不是形式** —— 它强迫模型把"数据"和"我改了什么"连上，
而那正是上次跳过的一步。诊断进日志 + 工作区的 `diagnosis.md`
（连着两轮说同样的话本身就是一个信号）。
⚠️ 而没有分隔符时不能报错 —— 第一轮不要求诊断。

## ⑤b3 「很暗淡」的真死因：雾（0.9.150 实测）

用户 2026-08-03 第二张（`wallpaper-08030141`）：「还是不太行，动态的部分太少了，
还很暗淡」。读数：高亮 **0%**、三带 8/10/10。

⛔ 死因是 **`FogExp2(BG, 0.12)` + 相机在 12m**：
`FogExp2` 的透光率 = `exp(-(density × distance)²)` = `exp(-(0.12×12)²)` ≈ **0.13**
⟹ 所有元素的亮度被乘掉 **87%**。模型把 L 给到 0.85，实际显示 **0.11**。

⚠️⚠️⚠️ 而模型**三轮都在调 L**。它的诊断每轮都很到位
（"根因不是系数"、"亮度没有以离中心距离做强衰减"），
但**没有一轮怀疑到雾** —— 因为雾在 `setHSL` **之后**作用，它看不见那个乘法。

⟹ 判据：**当一个参数的效果隔着好几层才显现，模型不可能靠试错找到它。**
那种参数要么由我们算（`DP.fogDensity(相机距离, 场景半径)`），
要么在观测报告里**把它的影响直接算出来摆给它看**（现在两件都做了）。

⚠️ 雾该做的是"让最外圈没入底色"：算出来的密度在近处透光 95%、
相机处 68%、最远 25%。而 0.12 是近处 40%、相机处 9%。

⛔ **空闲动画写在 `else` 里**（`if (hasAudio) {频谱} else {行波}`）
⟹ **有音乐时行波那一层整个消失**，而那正是"整片都在起伏"的来源。

## ⑤e 骨架是手段，不是笼子

用户 2026-08-02：「我给你的骨架仅仅是说一种想要在有限空间内高质量的一种手段，
本质上我们其实还是 agent，不要太死板了」

⟹ `FORBIDDEN` 那张表只拦两类：**会和骨架打架的**（两个渲染循环 / 两次 setSize）
和**在这个环境里跑不起来的**（import / require / fetch / HTML）。

⛔ 而这些是**明确允许**的，别加进闸门（`wallpaper-gen.js` 里写着，
`gating.test.js` 守着）：
`ctx.scene.remove(ctx.defaultLights)` 换整套打光 / 改 `scene.background` /
改 `scene.fog` / 相机的一切 / 自建 Texture、ShaderMaterial / `setTimeout` /
`Math.random`

⚠️ 判据：**闸门守的是"必然出事"，不是"不符合我的预期"。**
一条拦住了正确写法的闸门比没有闸门更贵 —— 它会让模型去改一段本来对的代码。
实测：F 闸门连着三轮误报粒子诞生位置的 `Math.random`，**模型每次都是对的**。

## ⑥ 右栅：两种模式共用一个槽位

`.pane-side` 里两个平级 body（壁纸参数 / AI 工坊），靠 `hidden` 互斥。
判据：**时间上互斥**（不会同时想看某张壁纸的参数和跟 AI 对话）。

- **收起是粘的**：收起之后再点壁纸**不会**顶开它。否则"收起"只活到下一次点击，
  而那种"我明明关了它又回来"是最烦的一类交互。
  ⚠️ 但打开 AI 工坊**会**解掉 —— 那是明确意图，点壁纸不是。
- **收起状态不进 config**：这是"我现在想多看几张壁纸"的临时动作，不是偏好。
  存下来的话下次打开发现面板不见了，而那时用户已经不记得自己收过。
- ⚠️ **展开把手放在 `.split` 里，不是 `.pane-side` 里** —— 收起就是给那块加
  `hidden`，把手在里面会跟着消失 ⟹ 判据：**隐藏某块的按钮不能放在那块里面。**

⚠️ **宽度是一档一档的**（`SIDE_STEPS = [340, 460, 580]`，默认最窄那档）——
不做无级拖拉，因为预览图有固定尺寸，无级宽度会让卡片一直在半格状态。
⟹ 而 `GRID_MIN = 460` 是**壁纸区**的最小宽度（用户点名的那条）：窗口不够宽时
那些挡位**禁用而不隐藏** —— 按钮数量一变位置就跳，而用户点的是位置。
⚠️ 宽度进 config（那是偏好），**收起状态不进**（那是临时动作）。

## ⑦ 给元素写了 `display` 之后，它的 `hidden` 就失效了

`hidden` 属性的实现是 **UA 样式表**里的 `[hidden] { display: none }`，
而**作者层 > UA 层**（层叠顺序的第一优先级，和选择器权重无关）。

⟹ `#ai-body { display: flex }` 让 AI 面板**从来没被藏住**（0.9.127~0.9.132
六个版本），一直挂在壁纸参数下面 —— 用户看到的是"参数下面一片空余 + AI 那一坨"。

⚠️ 而它伪装得很好：AI 没打开过时 `#ai-log` 是空的、输入框在最下面
⟹ 看起来就是"面板下方的留白"。

⚠️⚠️ 而**既有的三条守卫全都测不到它** —— 它们查 DOM 结构、查 JS 逻辑、
查 Esc 接线，全绿而面板一直可见。
⟹ 判据：**"逻辑对"和"用户看到的对"之间还有一层 CSS，那一层要单独测。**

⟹ 现在有一条全局兜底：`[hidden] { display: none !important }`（作者层）。
那是这个项目**唯一一处 `!important`**，而它是对的："hidden 就该不显示"
不存在例外。

## ⑧ "当前状态"不能靠"在列表里找一下"来表示

启动时装的壁纸是 `config.we.dir`（一条**绝对路径**），而壁纸列表扫的是
**当前**壁纸目录 ⟹ 两者不一致时（改名后搬了目录、或者手动挪过文件）
`item.active` 全是 false ⟹ **桌面上在放一张壁纸，而面板上没有任何东西对应它**。

用户 2026-08-02 报的就是这个：「这张壁纸我不知道为啥会自动运行，
而且我看那里也没有显示正在播放的壁纸」—— 不是它乱放，是面板没说放的是哪个。

⟹ 判据：**一个正在生效的状态，界面上必须有地方能看到它** ——
"在列表里找一下"不算，因为找不到的时候那个状态就从界面上消失了（而它还在生效）。
⟹ `workshop-local` 单独报 `activeDir` / `activeTitle` / `activeListed`，
面板据此提示，并给出可执行的下一步（不是只报告异常）。

⚠️⚠️ **而 0.9.128 那个启动闸门还引入了第二个缺口**（0.9.134 修）：
壁纸装载被推迟到 `launch-dismissed` 之后，而**面板的首次渲染在那之前** ——
`renderMine()` 拿到的 items 里每一项 `active` 都是 false（那时 `weProject` 还是
null）⟹ 轮播摘要行一直说"没有在放壁纸"，直到用户手动点一张。

⟹ 判据：**把一件事推迟之后，要问"谁在它之前已经读过那个状态了"** ——
那些读过的地方需要一次重读，而"推迟"本身不会通知它们。
⟹ 修法：装载完（**含回落到内置壁纸那一支**）广播 `we-status`，
面板收到就重扫列表。用现成的通道，不新造（这个项目为"新造一个没人听的频道"栽过）。

## ⑨ `.bar-row` 的第一格不放按钮

它是 `grid-template-columns: 1fr auto`（**两列**），第一格会被拉满。
"巨长按钮"这个症状**出现过三次，三次都是同一个原因**（AI 入口、工坊分页条、
诊断按钮行）。

⟹ 按钮排一行用 `.bar-row.tight`；子元素**个数不固定**时用 flex 而不是 grid
（固定列数的 grid 装不下变化的子元素个数）。

## ⑩ 删入口之前先问"这个功能的状态存在哪、谁还在读它"

0.9.130 删掉「壁纸动作」那一段 UI 时，`input.js` 的 `updateRecorded()` 遍历的是
`config.recorded` 里**所有**条目（不是"面板上显示的那些"）
⟹ 光删 UI 的话用户以前录过的手势会继续触发，而面板上再也找不到它们。
⟹ 加了一次性迁移清掉。

⚠️ 反过来那次也栽过：三层壁纸接好了而面板零入口 ⟹ 功能静默不可用。
⟹ 判据：**入口和状态要一起动。**

⚠️ 一次性迁移要**写死当时那批 id**，不能写成"凡是符合某规则的都清" ——
后者是一条会继续生效的规则，以后新加的东西会被误清。

## ⑪ 守卫自己会坏，而坏法只有几种

这一轮（0.9.120~0.9.131）反向验证逮到的死断言，**六次是同一件事**：

| 坏法 | 例子 |
|---|---|
| 关键词命中**注释** | `/position:\s*absolute/` 命中了"解释为什么需要它"的那句注释 |
| 关键词命中**模块导出** | `/parseResponse/` 命中了 `module.exports` 里那一行 |
| 关键词命中**失败消息自己** | 断言的 message 里写着它要查的那个表达式 |
| 关键词在那段里出现**多次** | "思考" 5 次 ⟹ 破坏一处其余还满足它 |
| **前缀匹配** | `/function aiSetOpen/` 命中 `function aiSetOpenX` |
| **固定长度切片** | `slice(at, at + 3000)` 跑过函数末尾吃到了 `module.exports` |

⚠️⚠️ 而这件事**第七次**发生时（0.9.134）我才做对：前六次我都在**逐条改断言**，
那是治症状。真因是 `codeOnly()` **名不副实** —— 它只过滤"整行以 `//` 开头"的，
而 `foo(); // 提到 bar` 这种**行尾注释留着**。
⟹ 修了那个函数（剥行尾注释，但引号内的 `//` 不动）⟹ 156 个调用点一次到位。
⟹ 判据：**同一个形状栽第二次就该问"这是不是工具的问题"**，而不是再改一条断言。

⟹ 判据：
- **匹配代码前先剥注释**（用 `codeOnly()`，别手写正则）
- **"这个词出现/不出现"从来不是可靠断言** —— 要锚**产生效果的那个语句形状**
- **切片要切到结构边界**（下一个 `function` / 下一个 `ipcMain` / `\n}`），别用固定长度
- **顺序守卫要盯"执行时机"**，文件位置只是一种近似 —— 近似失效的方式是"在正确代码上报红"
- 产品名/版本号这类会变的标识，**从单一来源读**（`PRODUCT = pkg.build.productName`）——
  0.9.131 改名时**五条守卫同时在正确代码上报红**，因为各自写死了旧名字

## ⑫ 云端验不了什么

我（云端）能验：纯函数、静态一致性、代码结构、LLM 调用本身。
**验不了**：Electron 窗口里长什么样、毛玻璃好不好看、340px 够不够读、
真机权限、`launch-dismissed` 的真实时序。

⟹ 那些结论**只能来自用户打包后的实测**。而这个项目为"我在云端下了一个
真机结论"栽过多次 ⟹ 判据：**说不了的就说"这条只能你验"**，别包装成事实。
